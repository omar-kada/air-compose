# Architecture

AirCompose is built as a single Go binary with a React frontend, packaged as a Docker image. Below is an overview of the system architecture and component interactions.

## Components

### Frontend (React SPA)

- Built with **React 19**, **TypeScript**, and **Vite**
- UI components from **Radix UI** with **Tailwind CSS**
- API client generated by **Orval** from the TypeSpec OpenAPI spec
- State management via **TanStack Query** and **TanStack Router** (with `react-router-dom` also available)
- Real-time updates via **WebSocket** connection for log streaming and event broadcasting

**Key pages:**
- Login / Register / Init
- Deployments (list + detail view with diff)
- Status (container health overview)
- Logs (real-time log viewer)
- Config (compose stack editor)
- Settings (Git, notifications, OIDC, schedule)

### Backend (Go)

The backend is organized into internal packages:

| Package | Responsibility |
|---|---|
| `cmd/air-compose` | Entry point; bootstraps CLI commands |
| `internal/cli` | Cobra-based CLI with `run` and `redeploy` subcommands |
| `internal/server` | HTTP server, routing, middleware |
| `internal/server/handlers` | HTTP request handlers (business logic) |
| `internal/server/socket` | WebSocket handler for log streaming |
| `internal/server/mappers` | Data mappers between API models and internal models |
| `internal/config` | YAML config file store with fsnotify-based file watching |
| `internal/deployments` | SQLite-backed deployment history storage |
| `internal/docker` | Docker Compose deployment, removal, health checks, inspection |
| `internal/events` | Event bus (fan-out), event store, notification handling |
| `internal/git` | Git repository synchronization via go-git |
| `internal/process` | Deployment orchestrator, scheduler, health transition handler |
| `internal/users` | Authentication (local + OIDC), session management |
| `internal/storage` | GORM/SQLite database initialization, pagination |
| `internal/shell` | Shell command executor |
| `internal/logs` | Log hub with ring-buffer history for WebSocket clients |
| `internal/models` | Domain types and enums |

### API Layer

The API is defined using **TypeSpec** (`/api/` directory), which generates:
1. An OpenAPI spec (`tsp-output/schema/openapi.1.0.yaml`)
2. Go server stubs (`backend/api/api.gen.go`) via `oapi-codegen`
3. TypeScript client (`frontend/src/api/api.ts`) via Orval

All routes are under `/api/` and require authentication (Bearer token or OIDC).

### Data Flow: Health Monitoring

```
HealthChecker (every 20s)
    │
    ┼──► docker.Inspector.GetCurrentStacks()
    │       ├── Lists all containers via Docker API
    │       ├── Matches to configured services by label
    │       └── Returns StacksState (service → container → status)
    │
    ├──► HealthTransitionHandler
    │       ├── Unhealthy? → DoDeploy (retry up to N times)
    │       └── Healthy? → Reset retry counter
    │
    └──► EventBus (HEALTH_CHANGE events)
            ├── WebSocket clients
            ├── Logger
            └── Notification handler (if enabled)
```

### Data Storage

| Storage | Technology | Purpose |
|---|---|---|
| `config.yaml` | YAML file | Application configuration |
| `air-compose.db` | SQLite (via GORM) | Deployments, events, users, sessions |
| `repo/` | Git clone | Local working copy of services repo |
| `air-compose.log` | JSON lines | Application log file |

### Self-Update Mechanism

When the `air-compose` service is included in the config, AirCompose spawns a temporary container to pull the latest image and restart itself:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  -v $SERVICES_DIR:$SERVICES_DIR -v $WORKDIR:$WORKDIR \
  $AIR_COMPOSE_IMAGE air-compose redeploy
```
