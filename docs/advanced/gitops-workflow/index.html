GitOps Workflow

AirCompose implements a GitOps deployment model: your Git repository is the single source of truth for Docker Compose stack configurations. When changes are detected, AirCompose automatically syncs and deploys.

Overview​

The GitOps workflow consists of these key stages:

  1. Poll the Git repository for changes
  2. Detect differences between local and remote
  3. Compute a patch (diff) of the changes
  4. Deploy affected stacks
  5. Monitor health and trigger retries if needed

Repository Structure​

Your configuration Git repository should follow this layout:

services/
├── web-app/
│   ├── compose.yaml
│   └── .env
└── database/
    ├── compose.yaml
    └── .env
  • Each subdirectory under services/ is a service stack
  • The stack name is derived from the directory name (e.g., web-app, database)
  • Each stack directory should contain a standard docker-compose.yaml file
  • Optional .env files can provide default environment values
note

The .env file is managed by AirCompose — it preserves your original entries and appends generated variables under a managed section (# The next values are generated by AirCompose :).

Sync Triggers​

There are three ways deployments can be triggered:

1. Scheduled Sync (Cron)​

When schedule.cron is set in the configuration, AirCompose polls the Git repository at the specified interval. The cron expression is evaluated using standard cron syntax.

Examples:

  • @hourly — every hour
  • */30 * * * * — every 30 minutes
  • 0 2 * * * — daily at 2:00 AM

When the cron fires, RepoWatcher.DeployOnChange checks if the remote repository has new commits. If changes are detected, a deployment is triggered.

2. Configuration Update​

When the config.yaml is modified (either via the UI or by direct file edit), AirCompose detects the change and triggers a deployment if the environment variables or service definitions have changed.

The file is watched using fsnotify, so changes are picked up in near-real-time.

3. Manual Sync​

You can trigger a sync manually at any time by clicking the Sync button in the UI. This immediately checks for repository changes and deploys if necessary.

Deployment Process​

When a deployment is triggered:

┌─────────────┐
│ Detect      │── Check if remote has new commits
│ Changes     │
└──────┬──────┘
       │
  Changes?
       │
  ┌────▼────┐   No    ┌─────────────┐
  │         │────────►│  Done       │
  │ Deploy  │         │ (no-op)     │
  │ Service │         └─────────────┘
  │         │
  └────┬────┘
       │ Yes
       ▼
┌──────────────────────────────────────────┐
│ 1. Create deployment record              │
│ 2. Pull changes into working branch      │
│ 3. Copy service files to services dir     │
│ 4. Generate .env file for each service   │
│ 5. Run `docker compose up -d`            │
│ 6. Update deployment status              │
└──────────────────────────────────────────┘

Differential Deployments​

AirCompose only deploys services that have changed:

  • Added services are deployed for the first time
  • Modified services are re-deployed using docker compose up -d
  • Removed services are stopped and removed with docker compose down

The diff is computed using go-git to compare the local HEAD with the remote branch.

Self-Update​

If the air-compose service is defined in your config, AirCompose will:

  1. Copy its own compose files to the services directory
  2. Run a temporary container to execute air-compose redeploy
  3. The redeploy command runs docker compose up -d to pull the latest image and restart

Health Monitoring​

After deployment, AirCompose monitors container health every 20 seconds:

Health StateAction
healthyReset retry counter
startingNo action (wait)
unhealthyTrigger redeploy (up to retriesOnUnhealthy times)
none (no healthcheck)Trigger redeploy if retriesOnUnhealthy > 0

Retries are spaced by retryDelay milliseconds. If the maximum retries are exceeded, no further automatic retries occur until the health status returns to healthy.

Working Branch​

AirCompose uses a temporary branch called to_be_deployed for applying changes before deployment:

  1. The config repo is cloned (or updated via fetch) into ./data/repo/
  2. Changes are checked out into the to_be_deployed working branch
  3. Files are copied from the working branch to the services directory
  4. Deployments run against the services directory

Event Types​

AirCompose emits events throughout the GitOps workflow:

EventTriggered When
NEW_COMMITNew changes detected in the Git repo
DEPLOYMENT_STARTEDA deployment begins
DEPLOYMENT_SUCCESSA deployment completes successfully
DEPLOYMENT_ERRORA deployment fails
HEALTH_CHANGEContainer health status changes
CONFIGURATION_UPDATEDConfig file is modified
ERRORA non-deployment error occurs
MISCInformational deployment events (e.g. services to remove, deploy list, working-branch updates)
note

PASSWORD_UPDATED and SESSION_REUSED are also valid event types, but they originate from the auth system (password changes / OIDC session reuse), not the GitOps deployment flow.
